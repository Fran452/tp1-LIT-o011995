Trabajo práctico integral

Construir una aplicación web con Lit

Desarrolla una pequeña aplicación con autenticación de usuario, navegación entre páginas y gestión del estado mediante localStorage. El objetivo es integrar los conceptos fundamentales de componentes web, eventos, propiedades reactivas y composición en Lit.

RequisitosComponentesEntrega

Objetivo del trabajo

Aplicar los conocimientos de Lit para resolver un caso de uso completo. La solución debe separar responsabilidades en componentes reutilizables y ofrecer una experiencia coherente para usuarios autenticados y no autenticados.

Idea central: el usuario podrá iniciar sesión, acceder a un catálogo protegido, cerrar sesión y conservar el estado de autenticación al recargar la página.
Aclaración sobre el ruteo: en este trabajo se utilizará @vaadin/router como herramienta de aprendizaje de Lit y de navegación en aplicaciones web. Aunque el ruteo utilizado en proyectos Cells puede resolverse con mecanismos propios del ecosistema Cells, esta práctica mantiene Vaadin para trabajar sus conceptos con el apoyo de GitHub Copilot.

Requisitos funcionales

Implementa los siguientes puntos en el orden indicado. Cada punto debe poder comprobarse ejecutando la aplicación.

  1. Crear la estructura inicial con Vite. Inicializa el proyecto utilizando Vite y selecciona una plantilla adecuada para trabajar con JavaScript y Lit. Organiza el proyecto en archivos y carpetas, separando páginas, componentes funcionales, layouts y servicios o utilidades. Consulta la documentación oficial de Vite para conocer el proceso de creación y configuración inicial.
  2. Crear la página de login. La ruta /login debe mostrar el formulario y permitir al usuario enviar sus credenciales.
  3. Validar el acceso. Para esta práctica no hace falta un backend. Usa las credenciales didácticas indicadas en la sección de entrega y define qué ocurre cuando son correctas o incorrectas.
  4. Crear la página Home. La ruta /home debe mostrar un catálogo o contenido privado que solo se vea después de iniciar sesión.
  5. Configurar la navegación. Usa @vaadin/router para resolver las rutas y navegar entre /login y /home.
  6. Persistir la sesión. Guarda, recupera y elimina el estado de autenticación usando localStorage.
  7. Proteger la ruta privada. Si una persona visita /home sin sesión, debe ser redirigida a /login antes de acceder al contenido.
  8. Implementar el logout. El menú de Home debe incluir una acción para cerrar sesión, borrar el estado persistido y volver a /login.

Componentes que debes crear

Cada elemento debe ser un Web Component desarrollado con Lit y registrado con un nombre personalizado. Evita concentrar toda la lógica en un único componente.

Página

login-page

Actúa como contenedor de la pantalla pública de acceso.

  • Renderiza el componente login-component.
  • Escucha los eventos login-success y login-error.
  • Cuando recibe login-success, solicita al router navegar a /home.
  • Cuando recibe login-error, guarda el mensaje y lo muestra mediante alert-component.
Componente funcional

login-component

Se ocupa exclusivamente del formulario y de la validación del acceso.

  • Incluye campos para usuario y contraseña.
  • Controla el envío del formulario y evita su recarga por defecto.
  • Comprueba las credenciales definidas para la práctica.
  • En caso correcto, guarda la autenticación y emite login-success.
  • En caso incorrecto, emite login-error con un mensaje útil.
Componente funcional

alert-component

Presenta mensajes al usuario sin conocer la lógica del login.

  • Recibe como mínimo un mensaje mediante una propiedad reactiva.
  • Permite distinguir visualmente un mensaje de error.
  • Solo se renderiza cuando existe un mensaje que mostrar.
  • Debe ser reutilizable para otros avisos de la aplicación.
Mixin reutilizable

CustomEventMixin

Crea un mixin que simplifique la emisión de eventos personalizados desde cualquier componente Lit. Su objetivo es evitar repetir en cada componente la construcción completa de un objeto CustomEvent y la llamada a dispatchEvent.

  • Debe ofrecer un método reutilizable, por ejemplo emitEvent(nombre, detalle, opciones).
  • El método debe crear y disparar el evento con el nombre y el detalle recibidos.
  • Configura por defecto las opciones necesarias para que el evento pueda atravesar el Shadow DOM y ser escuchado por el componente padre.
  • Permite modificar las opciones del evento cuando un caso lo necesite, sin duplicar la lógica del mixin.
  • Utiliza este mixin desde login-component para emitir login-success y login-error.
Página protegida

home-page

Representa el contenido disponible después de autenticarse. El alumno tiene libertad para decidir el diseño y el contenido de esta página, siempre que cumpla los requisitos mínimos.

  • Solo debe mostrar su contenido cuando el usuario está autenticado.
  • Utiliza el componente nav de Dile Components dentro de su menú. Consulta su documentación para conocer las propiedades, eventos y slots disponibles.
  • Incluye en el menú un botón o acción para realizar el logout.
  • Como sugerencia, puede incluir una breve presentación del alumno con sus datos, por ejemplo: nombre, curso, intereses, tecnologías que conoce o una descripción personal.

Eventos esperados

La comunicación entre componentes debe realizarse mediante eventos personalizados, evitando acoplar innecesariamente el formulario con la página que lo contiene. Para no repetir el código de creación y disparo de eventos, utiliza el mixin CustomEventMixin.

  1. 01

    Login correcto

    login-component emite login-success cuando las credenciales son válidas.

  2. 02

    Redirección

    login-page escucha el evento y el router navega hacia /home.

  3. 03

    Error de login

    Si las credenciales no son válidas, se emite login-error y se muestra alert-component.

Layouts y separación de responsabilidades

Los layouts definen la estructura común de cada tipo de pantalla. No deben contener la lógica específica del formulario ni del catálogo.

Layout público

public-layout

Es el contenedor de las vistas que no requieren sesión.

  • Incluye una estructura sencilla para mostrar login-page.
  • Utiliza un <slot> para recibir y renderizar el contenido de la vista pública.
  • Puede incluir la identidad visual de la aplicación y un pie de página.
  • No debe mostrar el menú privado ni opciones de logout.
Layout autenticado

auth-layout

Es el contenedor de las vistas disponibles para usuarios autenticados.

  • Debe tener las áreas header, main y footer (utilizar slots nombrados).
  • Utiliza el <slot> dentro de main para recibir el contenido de home-page.
  • El menú o header debe permitir ejecutar el logout.

Router, estado y protección

  1. Definir las rutas. Configura /login con public-layout y login-page. Configura /home con auth-layout y home-page.
  2. Resolver el ruteo con GitHub Copilot. Utiliza Copilot para investigar la configuración de @vaadin/router y proponer la estructura de rutas. Revisa y comprende cada propuesta antes de incorporarla al proyecto. Comprueba el resultado ejecutando la aplicación y corrige las sugerencias que no se ajusten a los requisitos.
  3. Definir una clave de almacenamiento. Usa una constante para la clave de localStorage, por ejemplo auth-user, en lugar de repetir textos por todo el código.
  4. Guardar la autenticación. Después de validar las credenciales, guarda un valor que indique que el usuario inició sesión.
  5. Recuperar la autenticación. Al cargar la aplicación, consulta localStorage para saber si existe una sesión.
  6. Crear el mixin de protección. Implementa un mixin reutilizable para los layouts. Este mixin debe verificar si el usuario está autenticado antes de permitir el acceso al layout protegido y redireccionar a /login si no existe una sesión válida. Este mixin no debe encargarse de validar el formulario ni de guardar las credenciales.
  7. Crear el logout. Elimina la clave almacenada y navega a /login. La siguiente visita a /home debe volver a estar protegida.
Importante: GitHub Copilot se utilizará únicamente para ayudar a implementar el ruteo con @vaadin/router. El mixin de protección de los layouts deberá diseñarse e implementarse como parte de la arquitectura de la aplicación, sin convertirlo en un mixin de autenticación.

Resumen de elementos a crear

Utiliza esta lista como checklist final. La aplicación debe incluir los siguientes ocho elementos, cada uno con una responsabilidad concreta.

  1. login-page: página pública que contiene el formulario, escucha sus eventos y decide cuándo mostrar un mensaje o navegar a Home.
  2. login-component: formulario que recoge y valida las credenciales, guarda el inicio de sesión y emite los eventos de resultado.
  3. alert-component: componente reutilizable que recibe un mensaje y muestra avisos, especialmente los errores del login.
  4. home-page: página protegida cuyo diseño y contenido son libres, siempre que utilice el menú nav de Dile Components y permita cerrar sesión.
  5. public-layout: layout para las vistas públicas, con un <slot> para renderizar el contenido de login-page.
  6. auth-layout: layout para las vistas protegidas, con header, main y footer, utilizando slots nombrados y un slot para el contenido de home-page.
  7. Mixin de protección de layouts: mixin que verifica si el usuario está autenticado y redirecciona a /login cuando intenta acceder sin una sesión válida. No valida el formulario ni guarda credenciales.
  8. CustomEventMixin: mixin que ofrece un método común para crear y disparar eventos personalizados, como login-success y login-error, sin repetir el código de CustomEvent y dispatchEvent.

Entregables

  • Código fuente completo de la aplicación.
  • Componentes Lit separados por responsabilidad.
  • Mixin de protección para los layouts y CustomEventMixin para emitir eventos personalizados.
  • Configuración funcional de @vaadin/router.
  • Persistencia del estado de autenticación con localStorage.
  • README breve con instrucciones para ejecutar el proyecto, credenciales de prueba y decisiones técnicas.

Credenciales sugeridas para la demo: usuario alumno · contraseña lit2026. No es necesario implementar un backend real; la validación puede ser local y exclusivamente didáctica.

Criterios de evaluación

  1. Componentización (25%). Componentes claros, reutilizables y correctamente registrados.
  2. Ruteo y uso de Copilot (20%). Rutas configuradas con @vaadin/router, navegación correcta, protección de /home y documentación del proceso de trabajo con GitHub Copilot.
  3. Eventos (15%). Uso de login-success y login-error para comunicar estados mediante CustomEventMixin.
  4. Estado (20%). Persistencia, recuperación y eliminación de la autenticación con localStorage.
  5. Layouts y UI (10%). Separación entre layout público y autenticado, con una interfaz usable.
  6. Documentación (10%). Instrucciones de ejecución y explicación breve de la solución.
